# HealthMate 项目答辩常见问题与简明回答

> 说明：本文档按当前代码实现整理，避免把需求文档中的规划功能误认为已完成能力。回答建议在答辩时根据现场追问适当展开。

## 一、项目背景与需求定位

### 1. 你们这个项目解决什么问题？

解决日常健康管理中“记录麻烦、数据分散、建议不够个性化、难以坚持行动”的问题。系统通过自然语言记录、AI 解析、趋势分析和任务打卡，形成健康管理闭环。

### 2. 为什么选择健康管理这个方向？

健康管理是高频、长期、个性化需求明显的场景，适合结合数据记录、可视化和大模型能力做辅助分析。

### 3. 系统的目标用户是谁？

主要是亚健康人群、健身初学者、职场人群等，希望改善睡眠、饮食、运动习惯的普通用户。

### 4. 这个系统是不是医疗系统？

不是。系统定位是日常健康辅助管理，不做疾病诊断、处方建议或医疗结论。

### 5. 为什么要强调非医疗诊断？

因为用户可能输入病痛症状，健康管理系统不能代替医生。代码中也做了高危内容识别，遇到病痛相关内容会拒绝保存并提示就医。

### 6. 相比普通健康记录 App，有什么特点？

核心特点是自然语言输入、AI 结构化解析、AI 建议、任务候选生成和用户确认机制，降低记录门槛并把建议转成行动。

### 7. 系统的核心业务闭环是什么？

健康档案 -> 自然语言记录 -> AI 解析预览 -> 用户确认保存 -> 趋势聚合 -> AI 建议 -> 候选任务 -> 用户选择 -> 打卡反馈。

### 8. 为什么需要任务打卡？

单纯给建议不一定能促成行动，任务打卡能把建议拆成当天可执行的小目标，帮助用户形成持续反馈。

### 9. 为什么任务不是自动创建？

为了避免 AI 生成的任务直接影响用户任务列表，系统先生成候选任务，让用户选择接受，增强可控性和用户确认。

### 10. 需求文档中的功能都实现了吗？

没有完全实现。当前实现的是核心业务闭环，像可穿戴设备同步、图片识别、社交排行、成就系统、语音输入、RAG 知识库等还没有完整落地。

## 二、系统功能与业务流程

### 11. 当前系统已经实现了哪些主要功能？

注册登录、健康档案、AI 健康记录解析、确认保存、首页仪表盘、趋势图、AI 建议流、任务候选生成、任务选择加入、任务打卡、个人中心。

### 12. 用户首次使用的流程是什么？

先注册/登录，然后完善健康档案，再进入首页或健康记录页，输入健康数据并使用后续建议和任务功能。

### 13. 健康档案保存哪些信息？

主要包括性别、身高、体重、健康目标、伤病史、过敏史等。

### 14. 为什么伤病史和过敏史要拆开？

因为它们对建议生成的影响不同。伤病史主要影响运动建议，过敏史主要影响饮食建议，拆字段更利于 AI 和业务逻辑使用。

### 15. 健康记录支持哪些类型？

支持饮食、运动、睡眠以及混合类型记录，字段包括摄入热量、运动消耗、睡眠分钟、饮食详情、运动详情和健康标签。

### 16. 用户一天可以记录多次吗？

可以。健康记录现在是新增记录，不再按天覆盖，适合早中晚多次记录。

### 17. 多条记录如何用于趋势分析？

后端按日期聚合。摄入和消耗通常求和，睡眠按记录聚合后统计，标签进行合并和分布统计。

### 18. 用户可以删除错误记录吗？

后端已实现健康记录历史查询和删除接口，用于删除误输入或过时记录，避免影响后续建议效果。

### 19. 前端是否已经完整接入健康记录删除？

当前代码中前端主要接入了最近记录和 AI 解析确认，完整历史/删除页面入口还可以继续补齐。

### 20. 首页展示哪些内容？

首页展示今日任务、任务完成进度、最近健康记录、最新建议和部分趋势摘要。

### 21. 趋势页展示哪些图表？

展示睡眠趋势、热量摄入/消耗趋势、健康标签分布等，支持周/月维度。

### 22. AI 建议是怎么展示的？

前端通过 EventSource 接收后端 SSE 流式返回的建议内容，呈现类似打字机的生成效果。

### 23. 任务页支持什么操作？

支持查看今日任务、查看历史任务、切换任务完成状态。

### 24. AI 生成任务后直接保存吗？

不会。先返回候选任务，用户勾选后才保存。

### 25. 用户选择新任务后会发生什么？

后端会归档或覆盖当前未完成任务，并把用户选择的新任务写入当天任务列表。

### 26. 为什么要覆盖未完成任务？

避免任务长期堆积，也让新任务能根据用户最新记录和状态进行优化。

## 三、AI 相关实现

### 27. 项目中 AI 主要用于哪些地方？

主要用于健康记录结构化解析、高危内容识别、健康建议生成和任务候选生成。

### 28. 健康记录 AI 解析的目标是什么？

把用户自然语言输入转成适合落库的结构化字段，例如睡眠分钟、摄入热量、运动消耗、饮食详情、运动详情和健康标签。

### 29. 为什么解析时要把数据库字段放进 Prompt？

为了让模型按落库字段输出，减少无关内容，提高结构化结果和后端模型的匹配度。

### 30. AI 解析结果会直接保存吗？

不会。解析接口只返回预览，用户确认后才调用确认接口保存。

### 31. 如果 AI 解析不出有效内容怎么办？

返回 shouldSave=false、失败原因和优化输入建议，前端提示用户补充更明确的信息，不保存记录。

### 32. 什么是解析置信度？

系统用 confidence 和 confidenceScore 表示解析结果可靠程度，低置信度时提示用户检查或补充信息。

### 33. AI 返回脏数据怎么办？

后端会做字段归一化和 Pydantic/业务校验，只提取允许的字段，避免直接信任模型输出。

### 34. 如果 LLM 不可用怎么办？

系统支持规则解析或 mock 兜底，保证核心流程仍能运行。

### 35. 高危内容如何识别？

优先用大模型判断是否涉及病痛、症状、疾病、用药、心理危机等超出日常健康管理范围的内容，同时使用正则规则兜底。

### 36. 为什么高危内容不保存？

因为病痛症状不适合作为普通健康打卡记录保存，系统应提示用户及时就医，而不是给出非专业建议。

### 37. 正则兜底的意义是什么？

当 LLM 不可用或判断失败时，仍能通过关键词规则识别明显风险，提升安全性。

### 38. AI 建议生成依赖哪些信息？

依赖用户档案、健康记录、任务记录、历史建议、健康总结等上下文。

### 39. AI 任务生成依赖哪些信息？

依赖用户档案、所有健康记录、所有任务及状态、今日已完成任务、今日未完成任务、最新建议和总结。

### 40. 如何避免生成重复任务？

后端会检查候选任务与今日已完成任务的相似度，相似则过滤；与未完成任务相似则倾向生成优化版任务。

### 41. 相似度如何判断？

当前主要用关键词重叠和字符串相似度，后续可以升级为 embedding 语义相似度。

### 42. 为什么没有使用 RAG？

当前版本以用户个人数据上下文为主，没有完整接入知识库检索，所以不能说已经实现 RAG。

### 43. AI 生成建议时是否会自动生成任务？

不会。建议生成和任务生成已经拆开，任务需要用户手动触发生成预览。

### 44. AI 相关接口是否绑定某个具体模型？

后端使用 OpenAI-compatible Chat Completions 格式，具体模型通过环境变量配置，具备一定可替换性。

### 45. Prompt 工程主要做了什么？

明确角色、输入上下文、输出 JSON 格式、字段名、保存条件、安全边界和禁止医疗诊断。

## 四、前端实现

### 46. 前端技术栈是什么？

React、Vite、Ant Design Mobile、React Router、Axios、ECharts、echarts-wordcloud、Framer Motion。

### 47. 为什么选择 React？

React 适合组件化开发，生态成熟，和 Vite 配合开发效率较高。

### 48. 为什么使用 Ant Design Mobile？

项目界面偏移动端健康管理场景，Ant Design Mobile 提供了表单、按钮、标签、Toast 等常用移动端组件。

### 49. 前端有哪些页面？

登录注册、档案设置、首页、健康记录、AI 建议、任务、趋势、个人中心。

### 50. 前端如何管理路由？

使用 react-router-dom，在 routes.jsx 中定义公开路由和需要登录的业务路由。

### 51. 前端如何处理登录状态？

登录后保存 token，接口请求通过 Axios 拦截器携带认证信息，路由守卫根据登录状态控制跳转。

### 52. 健康记录页的核心交互是什么？

用户输入自然语言，点击 AI 解析，前端展示结构化预览，用户可以修改字段，确认后保存。

### 53. 前端是否做了高危词判断？

前端有本地风险词预检查，用于提前提示；最终以后端 LLM+规则判断为准。

### 54. 为什么前端也要做风险预检查？

可以更早给用户反馈，减少不必要的后端请求，但不能替代后端安全校验。

### 55. AI 建议为什么用 SSE？

SSE 适合服务器向浏览器单向推送文本流，能让建议逐步展示，用户体验更好。

### 56. 为什么不用 WebSocket？

当前场景主要是后端向前端单向推送生成文本，SSE 更简单，足够满足需求。

### 57. 图表如何实现？

使用 ECharts 封装图表组件，展示睡眠、热量、标签等趋势数据。

### 58. 前端 API 如何组织？

在 services/api.js 中按 auth、profile、health、advice、task 分组封装接口调用。

### 59. 前端如何适配后端字段？

使用 backendMappers 等工具把后端字段转换成页面需要的结构，例如档案和解析结果映射。

### 60. 前端目前有哪些未完成或占位功能？

语音输入、成就系统、完整健康记录历史删除入口等还不完整，部分功能只是占位或后端已有接口但前端待接入。

## 五、后端实现

### 61. 后端技术栈是什么？

FastAPI、SQLAlchemy、MySQL、Pydantic、JWT、bcrypt、httpx，可选 Redis 缓存。

### 62. 为什么选择 FastAPI？

FastAPI 支持类型注解、自动接口文档、异步能力和 Pydantic 校验，适合快速实现 REST API。

### 63. 后端项目如何分层？

分为 api routes、schemas、services、repositories、models、core、db 等层次。

### 64. routes 层负责什么？

负责接收请求、调用服务层、返回响应，不承载过多业务逻辑。

### 65. services 层负责什么？

负责 AI 解析、风险识别、趋势聚合、任务生成、建议生成等核心业务逻辑。

### 66. repositories 层负责什么？

封装数据库查询和写入，减少接口层直接操作 ORM 的复杂度。

### 67. schemas 层负责什么？

定义请求和响应结构，进行字段校验和接口契约约束。

### 68. models 层负责什么？

定义 SQLAlchemy ORM 模型，对应数据库表结构。

### 69. 后端如何统一响应？

通过 core/response.py 和异常处理逻辑统一接口返回格式和错误处理。

### 70. 后端如何做认证？

使用 JWT token 认证，登录成功后前端携带 token 访问需要登录的接口。

### 71. 密码如何保存？

使用 bcrypt 哈希保存，不保存明文密码。

### 72. 后端有哪些主要接口模块？

auth、profile、health、advice、task、admin jobs。

### 73. auth 模块实现什么？

实现注册和登录，返回访问 token 和档案完成状态。

### 74. profile 模块实现什么？

实现用户健康档案的查询、新建和更新，包括伤病史、过敏史等字段。

### 75. health 模块实现什么？

实现健康记录解析、确认保存、手动保存、仪表盘、趋势、最近记录、历史记录、删除、导出和总结。

### 76. advice 模块实现什么？

实现 AI 建议历史查询和 SSE 流式建议生成。

### 77. task 模块实现什么？

实现今日任务、历史任务、任务打卡、任务候选生成和选择保存。

### 78. admin jobs 模块实现什么？

提供归档任务、生成周总结、预生成建议等管理接口，目前不是自动调度。

### 79. 为什么保留一些 legacy alias 接口？

为了兼容前端或早期设计文档中的接口路径，降低联调修改成本。

### 80. 后端如何接入大模型？

通过 httpx 调用 OpenAI-compatible chat completions 接口，模型地址、key、模型名通过环境变量配置。

## 六、数据库与数据模型

### 81. 主要数据库表有哪些？

t_user、t_health_record、t_daily_task、t_health_summary、t_advice_history。

### 82. t_user 保存什么？

保存用户账号、密码哈希、基础档案、健康目标、伤病史、过敏史等。

### 83. t_health_record 保存什么？

保存用户健康记录，包括原始输入、记录时间、睡眠、饮食、运动、标签、置信度和解析警告。

### 84. t_daily_task 保存什么？

保存每日任务，包括任务内容、任务日期、状态、AI 生成原因等。

### 85. 任务状态有哪些？

主要有未完成、已完成、已归档三类状态。

### 86. t_advice_history 保存什么？

保存用户历史 AI 建议文本，便于个人中心和建议页展示。

### 87. t_health_summary 保存什么？

保存周期性健康总结和趋势信息，用于后续建议上下文。

### 88. 健康记录为什么用 JSON 字段？

饮食详情和运动详情结构较灵活，用 JSON 可以保存 foods、mealType、items 等扩展信息。

### 89. 为什么取消 user_id + record_date 唯一约束？

因为用户一天可能多次记录，唯一约束会导致覆盖，不符合真实记录场景。

### 90. 删除健康记录时如何保证权限？

删除接口会基于当前登录用户查询记录，只允许用户删除自己的记录。

### 91. 趋势数据如何从记录表得到？

后端按日期分桶聚合健康记录，计算睡眠、摄入、消耗和标签分布。

### 92. CSV 导出导出什么？

导出用户健康记录相关数据，方便查看或备份。

## 七、安全、可靠性与边界

### 93. 系统有哪些安全措施？

JWT 鉴权、bcrypt 密码哈希、接口参数校验、高危健康内容识别、用户数据按 user_id 隔离。

### 94. 如何防止未登录访问业务数据？

需要登录的接口通过依赖项校验当前用户，未携带有效 token 会被拒绝。

### 95. 如何避免用户看到别人的数据？

查询和写入都绑定 current_user.user_id，接口只操作当前登录用户的数据。

### 96. 大模型输出不稳定怎么办？

通过严格 Prompt、JSON 输出要求、字段归一化、后端校验和规则兜底降低风险。

### 97. 如果 AI 给出医疗建议怎么办？

Prompt 中禁止医疗诊断和处方建议，同时高危内容会被拦截，不保存普通健康记录。

### 98. 如果用户输入“胸痛、头晕”等内容会怎样？

系统会识别为高危或超出日常健康管理范围，拒绝保存，并提示及时就医。

### 99. 是否会把用户隐私直接暴露给第三方？

当使用外部 LLM 时，确实需要发送必要上下文给模型服务。当前实现主要用于课程原型，后续可做脱敏、最小化上下文和隐私策略增强。

### 100. Redis 是必须的吗？

不是。Redis 是可选缓存；未配置或不可用时，后端会退回到进程内存缓存。

### 101. Celery 或定时任务实现了吗？

当前没有完整接入 Celery 自动调度，只提供了可手动调用的 admin job 接口。

### 102. 系统是否支持多端？

当前是 Web 前端，界面使用移动端组件风格，文档中提到的 React Native 移动端不是当前代码实现。

## 八、测试与部署

### 103. 项目如何启动？

后端安装 requirements 后运行 uvicorn，前端安装依赖后运行 npm run dev。

### 104. 后端接口文档在哪里？

FastAPI 自动生成接口文档，服务启动后可访问 /docs。

### 105. 前端如何配置后端地址？

通过前端环境变量或 Axios 基础配置指定后端 API 地址。

### 106. 你们做了哪些测试？

后端有基础服务测试和编译检查；前端主要通过联调和页面功能验证。当前测试覆盖还可以继续加强。

### 107. 有没有自动化测试？

后端 tests 目录下有服务层相关测试，但完整端到端测试和前端自动化测试还没有系统化补齐。

### 108. 是否已经 Docker 部署？

需求文档中有 Docker 部署规划，但当前汇报应以代码实现为准，不能作为已完成重点功能展示。

### 109. 项目目前适合生产环境吗？

当前更偏课程项目原型，核心业务可运行，但生产化还需要补充迁移管理、日志监控、隐私合规、自动化测试和部署流程。

### 110. 数据库迁移如何处理？

当前模型已定义，但正式生产中建议引入 Alembic 管理表结构迁移。

## 九、项目设计取舍

### 111. 为什么不直接做表单记录？

表单记录准确但门槛高，自然语言更符合用户日常表达，再由 AI 转换成结构化字段。

### 112. 为什么解析后还要用户确认？

AI 可能误判，确认流程可以避免错误数据直接入库，提升数据质量。

### 113. 为什么还保留手动保存接口？

为了兼容旧流程和特殊场景，也方便前后端联调。

### 114. 为什么建议和任务要拆开？

建议是解释性内容，任务是行动项。拆开后用户可以先看建议，再决定是否生成和接受任务。

### 115. 为什么任务要考虑历史完成率？

如果用户完成率较低，系统应生成更简单、更容易完成的任务，提升持续使用概率。

### 116. 为什么使用 SSE 而不是普通 HTTP 返回完整建议？

流式返回能减少等待感，适合 AI 文本生成场景。

### 117. 为什么要保存 advice history？

方便用户回看历史建议，也能作为后续生成任务或建议的上下文。

### 118. 为什么需要 health summary？

summary 可以沉淀周期性健康趋势，减少每次 AI 生成都重新理解所有数据的压力。

### 119. 为什么当前 AI 任务候选数量有限？

当天任务应短小可执行，数量过多会降低完成率，所以限制候选数量更符合使用习惯。

### 120. 为什么任务要过滤与今日已完成任务相似的内容？

避免用户已经完成过的行为被重复要求，提升任务生成的合理性。

## 十、可能被追问的功能细节

### 121. 用户输入“今天吃了鸡胸肉沙拉，跑步 30 分钟”会发生什么？

AI 解析出饮食和运动信息，生成摄入/消耗估计、饮食详情、运动详情和标签，用户确认后保存。

### 122. 用户输入“我胸口疼”会发生什么？

系统识别为病痛高危内容，拒绝保存普通健康记录，并提示及时就医。

### 123. 如果用户修改了解析结果，以哪个为准？

以后端确认接口收到的用户修改数据为准，再进行校验后保存。

### 124. 如果用户今天记录三次饮食，趋势页怎么算？

后端按天聚合，多条饮食记录的摄入热量会合并统计。

### 125. 如果用户删除历史记录，会影响建议吗？

会。后续生成建议和任务时使用的是数据库中剩余的历史记录。

### 126. 如果用户没有完善档案能使用吗？

登录后会根据 profileCompleted 引导用户完善档案，档案越完整，建议越个性化。

### 127. 如果没有健康记录，AI 还能生成建议吗？

可以生成较泛化建议，但个性化程度会下降。系统更鼓励先记录数据。

### 128. 如果任务生成没有候选怎么办？

后端会返回 skippedReasons 说明原因，例如今日已完成或未完成任务已覆盖主要方向。

### 129. 用户能否取消已完成任务？

任务接口支持状态切换，前端任务页可以进行打卡/取消类操作。

### 130. 个人中心展示什么？

展示用户档案、伤病史、过敏史、最近记录、最近建议和快捷操作等。

## 十一、实现不足与后续优化

### 131. 当前项目最大的不足是什么？

生产化能力不足，例如完整迁移、自动化测试、日志监控、隐私合规和部署流程还需完善。

### 132. AI 解析还有什么优化空间？

可以引入更强的模型、few-shot 示例、字段置信度、人工反馈闭环和更精细的食物热量估算。

### 133. 高危识别还有什么优化空间？

可以增加风险等级、更多医学安全规则、审核日志，以及更明确的用户提示文案。

### 134. 任务生成还有什么优化空间？

可以使用 embedding 做语义去重，引入用户偏好、任务完成时间和长期目标分解。

### 135. 趋势分析还有什么优化空间？

可以增加更多维度，例如体重变化、运动频率、睡眠规律性、热量缺口等。

### 136. 前端体验还有什么优化空间？

补齐健康记录历史和删除页面、优化移动端适配、增加空状态引导、完善错误提示。

### 137. 后端工程化还有什么优化空间？

引入 Alembic、结构化日志、更多单元测试、集成测试、CI/CD 和正式任务调度。

### 138. 隐私保护后续怎么做？

可以对发送给 LLM 的上下文做最小化、脱敏处理，并提供用户数据删除和导出能力。

### 139. 如果后续接入可穿戴设备，怎么扩展？

可以新增设备数据表和同步服务，将步数、心率、睡眠等数据接入现有趋势和建议上下文。

### 140. 如果后续做图片识别饮食，怎么扩展？

可以新增图片上传接口和图像识别服务，将识别结果转换成 nutrition_details，再走确认保存流程。

## 十二、答辩时可用的总结回答

### 141. 一句话介绍项目？

HealthMate 是一个把自然语言健康记录转成结构化数据，并通过 AI 建议和任务打卡形成健康管理闭环的 Web 系统。

### 142. 一句话介绍技术架构？

前端使用 React + Vite，后端使用 FastAPI + SQLAlchemy + MySQL，AI 通过 OpenAI-compatible 接口接入，并用 REST API 和 SSE 完成通信。

### 143. 一句话介绍 AI 创新点？

AI 不只是生成文本，而是参与结构化解析、风险识别、个性化建议和任务候选生成，并通过用户确认机制控制落库和任务写入。

### 144. 一句话说明系统边界？

系统只做日常健康辅助管理，不做医疗诊断，病痛和高危内容会提示用户及时就医。

### 145. 一句话说明当前完成度？

当前已完成注册登录、档案、记录、解析、建议、任务、趋势和个人中心等主流程，可支撑完整演示。

## 十三、轻量级 RAG 与知识增强

### 146. 项目里的 RAG 是什么？

项目中的 RAG 是轻量级知识增强机制，会从本地健康知识库检索相关片段，并注入 AI Prompt，辅助健康记录解析和健康建议生成。

### 147. 为什么要引入 RAG？

为了让 AI 建议不只依赖模型自身知识，而是结合项目维护的健康知识库，提高建议的场景贴合度、依据性和边界控制能力。

### 148. RAG 用在哪些业务场景？

主要用于两个场景：健康记录 AI 解析和 AI 健康建议生成。

### 149. RAG 是否改变了前端交互？

没有明显改变。它主要是后端内部增强能力，前端仍然走原来的记录解析、建议生成和任务流程。

### 150. RAG 是否是一个独立问答系统？

不是。当前 RAG 是现有 AI 流程的知识增强层，不是多轮健康问答产品。

### 151. 知识库放在哪里？

知识库位于 `backend/app/data/knowledge/`，以 Markdown 文件形式维护。

### 152. 知识库包含哪些主题？

包括睡眠、营养、运动、体重管理、健康风险、慢病生活方式边界、心理与压力、健康记录规范和来源说明。

### 153. 为什么用 Markdown 做知识库？

Markdown 轻量、易维护、适合课程项目快速迭代，也方便按标题切分成知识片段。

### 154. 知识库内容来自哪里？

内容参考公开权威健康资料后进行场景化改写，并在 `sources.md` 中说明来源方向，不直接复制外部文章。

### 155. KnowledgeService 负责什么？

负责加载 Markdown 知识库、按标题切分知识块、执行检索，并把检索结果渲染成 Prompt 可用的上下文文本。

### 156. 知识库如何切分？

主要按 Markdown 的二级标题 `##` 进行分块，每个知识块包含 source、title 和 content。

### 157. 检索接口是什么？

核心接口是 `search(query, top_k)`，返回匹配的知识片段；`render_context(query)` 会把片段拼接成可注入 Prompt 的文本。

### 158. top_k 是什么意思？

表示每次检索最多返回多少个知识片段，默认配置为 3。

### 159. RAG 的配置项有哪些？

主要有 `KNOWLEDGE_ENABLED`、`KNOWLEDGE_DIR`、`KNOWLEDGE_TOP_K` 和 `KNOWLEDGE_EMBEDDING_MODEL`。

### 160. KNOWLEDGE_ENABLED 有什么作用？

它是知识增强开关，可以一键开启或关闭 RAG 注入。

### 161. RAG 检索使用什么方式？

优先使用 `sentence-transformers` 生成 embedding 做相似度检索；如果依赖或模型不可用，会自动降级为关键词检索。

### 162. 为什么要保留关键词检索兜底？

为了保证环境缺少 embedding 模型时系统仍能运行，不影响核心业务流程。

### 163. 当前 embedding 模型配置是什么？

默认配置为 `BAAI/bge-small-zh-v1.5`，用于中文语义检索。

### 164. 如果 sentence-transformers 没装会怎样？

KnowledgeService 会捕获异常并返回关键词检索结果，不会导致系统整体不可用。

### 165. RAG 如何增强健康建议生成？

AdviceService 会根据健康目标、健康标签、近期记录和健康总结构造 query，检索知识库后把 `knowledge_context` 放入 LLM 上下文。

### 166. RAG 如何增强健康记录解析？

HealthAIParseService 会从用户原始输入中提取关键词，检索相关健康知识，并把知识片段加入解析器 system prompt。

### 167. RAG 会直接决定保存哪些数据吗？

不会。RAG 只提供知识上下文，最终保存仍由解析结果、后端校验、高危识别和用户确认流程共同控制。

### 168. RAG 会替代高危识别吗？

不会。高危识别仍由大模型风险判断和正则规则兜底完成，RAG 只是辅助模型理解边界。

### 169. RAG 会替代规则解析吗？

不会。LLM 不可用时仍会走规则解析兜底，RAG 主要服务于 LLM 模式下的 Prompt 增强。

### 170. RAG 注入 Prompt 时有什么限制？

Prompt 明确要求知识片段只用于辅助判断，不要原样复述，不做医疗诊断、处方或治疗建议。

### 171. 为什么不把知识片段直接展示给用户？

当前前端主要展示建议和解析结果，知识来源展示还不是主流程；后续可以在建议下方折叠展示参考依据。

### 172. RAG 对任务生成有直接作用吗？

当前任务生成主要基于用户档案、健康记录、任务历史和建议上下文；RAG 直接接入的是解析和建议生成。

### 173. RAG 和普通 Prompt 拼接有什么区别？

普通 Prompt 主要依赖固定规则和用户数据；RAG 会先按当前场景检索相关知识，再动态注入更贴合的上下文。

### 174. 为什么说这是轻量级 RAG？

因为它使用本地 Markdown 知识库和简单检索服务，没有引入复杂向量数据库、多轮问答或引用展示系统。

### 175. 为什么没有使用专业向量数据库？

当前知识库规模较小，本地内存检索已能满足课程项目需求，架构更简单、部署成本更低。

### 176. 知识库规模大概是多少？

当前有 9 个 Markdown 文件，按主题切分后约几十个知识块，覆盖日常健康管理的主要场景。

### 177. RAG 如何提升建议具体性？

当检索命中明确知识时，AI 更容易生成具体行动建议，例如久坐场景下给出定时起身活动的建议。

### 178. RAG 如何提升安全边界？

知识库包含健康风险和慢病边界内容，能辅助模型避免诊断、用药调整等超出系统定位的回答。

### 179. RAG 是否会增加响应时间？

会有少量检索开销，但知识库规模较小，且检索在后端本地完成，对当前原型影响较小。

### 180. RAG 是否依赖外部网络？

知识库检索本身不依赖外部网络；如果首次加载 embedding 模型需要下载模型，则可能依赖环境配置。关键词兜底不需要网络。

### 181. RAG 的结果会存入数据库吗？

当前主要作为 Prompt 上下文使用，AdviceResult 中可携带 knowledge_context，但主业务保存的是建议文本和健康记录。

### 182. 如何评估 RAG 有没有效果？

项目提供了对比和评估脚本，对同一批健康场景分别运行 No RAG 和 RAG，并比较知识命中、建议长度、数字化建议和行动项等指标。

### 183. 评估脚本有哪些？

主要有 `backend/scripts/compare_rag_advice.py` 和 `backend/scripts/evaluate_rag_advice.py`。

### 184. rag_evaluation_results.json 是什么？

它保存批量评估结果，包括无 RAG / 有 RAG 的建议文本、检索片段数、知识命中等信息。

### 185. RAG 的评估结论是什么？

在知识库覆盖充分且检索命中明确的场景中，RAG 通常能让建议更具体、更贴近健康管理场景。

### 186. RAG 是否所有场景都一定更好？

不一定。RAG 效果依赖知识库覆盖范围、检索 query 质量和模型对上下文的使用能力。

### 187. 如果检索不到知识会怎样？

知识上下文为空，系统仍按原有 LLM Prompt 或规则兜底流程运行。

### 188. 如果检索到不相关知识怎么办？

当前通过 top_k 和相似度排序减少干扰，后续可以通过标签、query 重写和人工评估继续优化。

### 189. RAG 是否会泄露用户隐私？

RAG 检索本地知识库本身不泄露隐私；但调用外部 LLM 时仍需发送必要上下文，后续可以做更细的脱敏和最小化处理。

### 190. RAG 对健康记录解析有什么实际帮助？

它能帮助模型更稳定地区分饮食、运动、睡眠、风险边界和低质量输入，从而提高结构化解析质量。

### 191. RAG 对 AI 建议有什么实际帮助？

它能让建议更容易结合睡眠、饮食、运动等知识背景，减少空泛建议，提升可执行性。

### 192. 为什么知识库里有 health_risk？

用于帮助模型识别哪些内容超出日常健康管理范围，比如胸痛、呼吸困难、严重眩晕、心理危机等。

### 193. 为什么知识库里有 user_recording？

用于指导模型判断什么样的输入适合保存为健康记录，以及如何给用户更明确的补充输入建议。

### 194. 如果老师问 RAG 和 fine-tuning 区别，怎么回答？

RAG 是检索外部知识后注入 Prompt，不改变模型参数；fine-tuning 是用数据训练模型参数。我们选择 RAG 是因为更轻量、可控、便于更新知识。

### 195. 如果老师问为什么不用 LangChain，怎么回答？

当前需求只需要本地知识加载、切分、检索和 Prompt 注入，自研 KnowledgeService 更轻量，也更容易展示核心逻辑。

### 196. 如果老师问 RAG 的核心代码在哪里，怎么回答？

核心在 `backend/app/services/knowledge.py`，接入点在 `backend/app/services/advice.py` 和 `backend/app/services/health_parse_ai.py`。

### 197. 如果老师问怎么关闭 RAG，怎么回答？

在环境变量中设置 `KNOWLEDGE_ENABLED=false` 即可关闭知识增强。

### 198. 如果老师问 RAG 是否影响原接口兼容性，怎么回答？

基本不影响。它是后端内部上下文增强，原有 API 路径和前端调用方式保持稳定。

### 199. 如果老师问 RAG 最大价值是什么，怎么回答？

最大价值是让 AI 输出结合项目可维护的健康知识库，提升建议依据性、场景贴合度和安全边界控制。

### 200. 一句话介绍项目里的 RAG？

HealthMate 的 RAG 是一个轻量级知识增强层，通过本地健康知识库检索，把相关知识注入 AI 上下文，辅助健康记录解析和个性化建议生成。
